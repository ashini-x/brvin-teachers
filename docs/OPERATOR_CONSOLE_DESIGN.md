# BRVIN Teachers — Operator Console UX and Visual Design

**Status:** Operator Console, classroom/collection/source screens and persistent five-stage source progress stepper deployed; BRVIN Production registration and one-time connection proof accepted  
**Decision date:** 6 November 2026  
**Product:** BRVIN Teachers Operator Console  
**Implementation repository:** `ashini-x/brvin-teachers`  
**BRVIN core repository:** `ashini-x/parmar-ai`

This is the canonical UI/UX design and implementation reference for the central operator console. PR #1 deployed the shell and teacher-profile slice. PR #2 deployed classroom, bookshelf/collection and PDF source workflows plus the consumer management adapter. The Core management entrypoint is also deployed. Management actions remain fail-closed until the production `brvin-teachers` application/environment UUID is registered and configured.

## 1. Product experience

Build one central, protected Operator Console for platform operators to onboard and operate many teacher workspaces. The operator must be able to create a named teacher, enter that teacher's workspace, create subject classrooms/projects, organize collections/bookshelves, register document sources and inspect processing/usage without manually creating IDs or switching between unrelated admin interfaces for routine work.

The console is the primary day-to-day operating surface for BRVIN Teachers. BRVIN Admin remains the authoritative knowledge-governance backend and advanced administration surface. The console must use a narrow authenticated management integration with BRVIN; it must never access BRVIN D1, GCS or AI Search directly.

### Core interaction principle

**Create teacher → open workspace → create classroom → create bookshelf → upload documents.**

The operator supplies human names and content. The owning backend generates immutable system IDs and human-readable reference codes. The UI displays both, but does not let the operator invent or override either.

## 2. Teacher naming and identity

Teacher names are fully custom. "Teacher A", "Teacher B" and similar labels are only examples in documentation, never fixed product labels.

### Create Teacher form

Required:
- **Teacher name** — operator-facing display name, for example `Aditya Ranjan` or `Radhika Goel`.

Optional:
- **Student-facing display name** — the name students see, for example `Aditya Sir`. If omitted, default to the teacher name.
- A short operator note may be added later if real workflow requires it; do not collect unnecessary personal data in MVP.

After successful creation, show:
- Human-readable tenant reference, e.g. `TCH-000001`.
- Immutable internal tenant UUID, generated by the BRVIN Teachers application database.

Names are not unique identifiers. Two teachers may have identical names and must still create separate tenants. Never derive the ID/reference from a name, require names to be unique, or use a name as authorization. A teacher-name edit must not change tenant UUID or reference.

### Names at every level

Use editable names for:
- Teacher/workspace.
- Classroom/project, normally a subject or a deliberately isolated subject/class combination (e.g. `Mathematics`, `Physics — Class 10`).
- Bookshelf/collection (e.g. `Notes`, `Shortcuts and Tricks`).
- Source/document title (e.g. `Algebra Notes — Chapter 1`).

The name is descriptive metadata. The system reference and immutable UUID are generated by the owning backend. Renaming changes the label only, never the identifiers.

## 3. Information architecture

### Global application shell

Use one application shell with a persistent, collapsible left navigation on desktop and a slide-in navigation drawer on small screens.

Primary navigation:
1. **Overview** — concise platform health and high-level counts.
2. **Teachers** — searchable teacher directory and create-teacher action.
3. **Knowledge** — cross-teacher project, collection and source discovery for authorized operators.
4. **Processing** — uploads, OCR/indexing pipeline status and failed/retryable jobs.
5. **Usage** — retrieval quota, model usage and cost summaries, clearly distinguished.
6. **Activity** — administrative actions, grant/share/revoke history and audit events.
7. **Settings** — operator access and platform configuration.

Do not show invented totals or fabricated live status. Empty states should explain what has not been configured and provide the next legitimate action. Hide unavailable controls or label future capabilities explicitly rather than presenting inert buttons.

### Teacher directory

The Teachers page contains:
- Search by teacher name or human-readable reference.
- Filters for status and subject.
- Compact teacher rows/cards showing custom name, tenant reference, status, offered subjects and last activity.
- A clear **Create teacher** primary action.
- An explicit empty state for a new installation.
- No public/private student details in directory summaries.

Selecting a teacher opens that teacher's workspace.

### Teacher workspace

Header:
- Custom teacher name.
- Tenant reference.
- Status.
- Copy-reference action.
- Rename/edit and lifecycle actions, protected by confirmation when destructive.

Workspace navigation:
- **Overview** — summary, classrooms, readiness and recent activity.
- **Classrooms** — the teacher's BRVIN knowledge projects.
- **Students** — tenant-scoped student identities and subject enrolments, when implemented.
- **Channels** — tenant's registered Telegram/WhatsApp/web identities, when implemented.
- **Configuration** — teaching style, language, response format and enabled capabilities.
- **Usage** — teacher-attributed retrieval and model spend.
- **Activity** — actions scoped to this teacher.

Do not create a separate dashboard, Worker, D1 or GitHub repository for each teacher.

### Classroom/project workspace

Display:
- Custom classroom/project name and reference code.
- Subject/category and optional class/syllabus scope.
- BRVIN project readiness and authorized source count.
- Collections/bookshelves belonging to or available to this project.
- Add classroom, create collection and inspect project actions.

A new subject normally creates a project according to the approved one-project-per-teacher-subject knowledge-boundary default. Do not create one project per PDF, student or channel. A separate project is appropriate when the knowledge must be isolated (e.g. strict Class 9 vs Class 10 material, or strict Notes vs Shortcuts retrieval under the current project-scoped v2 contract).

### Collection/bookshelf workspace

Display:
- Collection name and reference.
- Origin/owning teacher and project.
- Whether it is owned or shared.
- Source list, source readiness and actions.
- Explicit share/grant management for authorized operators.

One collection may be granted to multiple projects. A grant does not clone, transfer or renumber the collection or its sources. The receiving workspace must visibly label material as shared and identify its origin where appropriate. Revocation must account for both collection grants and independent direct-source/book grants.

### Source/document details

Each source row/card should show:
- Custom document title.
- Source reference code.
- Internal BRVIN source ID in a technical-details disclosure/copy action.
- Original filename, page count and file size where available.
- Processing state and indexed/expected pages.
- Upload/processing activity and safe retry action where supported.

Processing states must reflect actual backend events, for example:
- Registered
- Uploading
- Queued / OCR processing
- Indexing
- Quality check
- Ready
- Failed / retryable (only where backend says so)

Never let the UI manually mark a source READY. Do not create a second source when resuming a failed or interrupted upload. Reuse the existing BRVIN source record and idempotency key.

## 4. Automatic identity and reference creation

Follow [IDENTIFIER_POLICY.md](IDENTIFIER_POLICY.md) as the normative format.

Examples:
- Tenant: `TCH-000001`.
- Project: `TCH-000001-PRJ-001`.
- Collection: `TCH-000001-PRJ-001-COL-001`.
- Source: `TCH-000001-PRJ-001-COL-001-SRC-001`.

At each creation step:
1. The UI submits the human-entered name and validated parent context only.
2. The owning backend/database generates its permanent UUID/system ID and allocates the next parent-scoped reference atomically.
3. The backend returns the created record and both identifiers.
4. The UI renders the human-readable reference prominently and the UUID/system ID in a copyable technical-details disclosure.
5. The UI uses the actual returned internal ID for subsequent API relationships and operations.

Never calculate the next number in the browser, use `COUNT(*) + 1`, or guess a number based on directory rows. Concurrent requests must not duplicate identifiers. Gaps are acceptable; reused numbers and duplicates are not.

Names and references are different. Editing a name never changes either identifier. References are not credentials or authorization.

## 5. Cross-system provisioning and failure handling

Teacher tenant records live in the BRVIN Teachers application D1. Knowledge projects, collections and sources live in BRVIN's registry in `parmar-ai`. Their creation therefore crosses two separately owned databases and cannot be described as one atomic SQL transaction.

### Teacher creation

- Create the tenant and allocate its UUID/reference in BRVIN Teachers D1.
- Do not silently create an application-project grant or assume that a project is ready.
- If the flow offers an optional initial classroom, provision it as a separate, resumable BRVIN management operation after the tenant exists.
- Show precise states such as `Created`, `Provisioning classroom`, `Needs attention` and `Active` according to real backend state.

### Project/collection/source management

- BRVIN Teachers calls a narrowly scoped, authenticated BRVIN management interface hosted by BRVIN's control/admin plane.
- BRVIN validates the external tenant reference and the requested parent relationship, then creates the project/collection/source in its own registry and allocates its own system ID/reference.
- The consumer stores the real BRVIN project ID and reference in its tenant-to-project mapping. It must not mirror the BRVIN collection/source registry or source content.
- Upload, OCR and indexing continue through the existing BRVIN ingestion pipeline and controls.
- Application-project access grants are explicit, audited and only issued when the consumer environment is ready for the approved integration.
- The current retrieval v2 methods remain the retrieval interface; do not overload them with administrative writes.

Because a cross-system operation can partially succeed, model it as a durable, idempotent workflow with a correlation/request ID and safe retry. The UI must distinguish:
- tenant creation succeeded but initial project provisioning failed;
- project was created in BRVIN but consumer mapping was not confirmed;
- upload transferred but OCR/indexing remains in progress;
- source is ready but a required grant/connection is absent.

Never display a success state that was not confirmed by the owning backend. A retry must reconcile by operation ID and must not create duplicate projects, collections, sources or grants.

## 6. Visual design system — ChatGPT-inspired dark

The approved direction is a restrained, professional, ChatGPT-inspired dark interface. It is **not Apple-inspired**.

### Color and surfaces

Use a low-contrast charcoal hierarchy:
- Application canvas: near `#212121`.
- Sidebar: darker charcoal near `#171717`.
- Main cards/panels: near `#2F2F2F`.
- Elevated/hover surfaces: near `#383838`.
- Borders/dividers: subtle charcoal gray near `#424242`.
- Primary text: near `#ECECEC`.
- Secondary text: neutral gray near `#A3A3A3`.
- Muted/disabled text: darker neutral gray, maintaining readable contrast.
- A single restrained BRVIN accent may be used for primary actions and active navigation. Reserve green/amber/red for meaningful status states, not decoration.

These are initial design tokens to tune during implementation and accessibility review, not a claim that they are official OpenAI design tokens.

### Typography

- Use a clean, highly legible sans-serif with a restrained text hierarchy similar in spirit to ChatGPT.
- Prioritize readable body text, clear heading hierarchy and compact metadata.
- Use consistent weights; avoid oversized hero typography, thin decorative fonts or excessive letter spacing.
- Reference codes and UUIDs use a legible monospaced treatment only where it improves scanning/copying.

### Cards, borders and controls

- Compact, content-first cards with subtle borders and consistent corner radii.
- Avoid glassmorphism, frosted surfaces, glossy gradients, large decorative shadows, neon glows, or oversized Apple-style tiles.
- Use neutral buttons with clear primary/secondary/destructive hierarchy.
- Use consistent outline icons (Lucide-style), mostly monochrome, with restrained size and stroke.
- Keep labels, helper text and metadata close to the controls they describe.
- Avoid turning every line of information into a separate card; use compact lists and tables where they scan better.

### Animation and interaction

- Minimal purposeful motion: short hover/focus transitions, subtle drawer/modal movement, restrained skeleton loading and clear progress indicators.
- Use approximately 120–180 ms for simple hover/focus transitions; respect reduced-motion preferences.
- No decorative orbs, ambient edge glows, shimmering backgrounds or perpetual pulsing.
- Use explicit loading, success and error feedback; do not show optimistic success for cross-system operations.
- Toasts are brief and non-blocking. Destructive actions require a contextual confirmation.

### Layout and responsive behavior

- Desktop: fixed/collapsible left sidebar, compact top header/breadcrumbs, wide central content with consistent max-width and aligned cards/tables.
- Tablet: collapsible navigation and adaptable two-column content.
- Mobile: slide-in navigation, stacked cards, horizontally manageable tables or list alternatives, touch-friendly controls and persistent access to key actions.
- Keep navigation and content usable on narrow screens; do not shrink desktop tables until they become unreadable.

### Brand boundaries

Use a ChatGPT-inspired interaction language and restrained dark visual hierarchy, but do not use OpenAI logos, claim OpenAI affiliation, or copy proprietary marks. BRVIN Teachers retains its own name, identity and product accent.

## 7. Accessibility, safety and operator trust

- Provide keyboard navigation, visible focus, semantic headings/labels and screen-reader names for icon-only actions.
- Ensure status is conveyed by text/icon as well as color.
- Respect reduced-motion preference.
- Require authentication and role checks for the entire Operator Console.
- Teacher-scoped future roles can access only their own workspace and cannot manage another tenant.
- Never rely on obscured UI controls for authorization; enforce all operations server-side.
- Do not expose credentials, student private data, raw source content or internal admin secrets in list views, URLs, logs or client state.
- Reference codes and UUIDs are identifiers, not access credentials.
- Confirm archive, delete, revoke and cross-teacher share actions with clear consequences.

## 8. MVP implementation order

1. Protected application shell, navigation, dark design tokens and empty states.
2. Teacher directory, search and custom-name tenant creation with auto-generated UUID/reference.
3. Teacher workspace and subject classroom/project creation.
4. Secure BRVIN management integration for projects, collections, sources, uploads and grants.
5. Processing/status views and failure recovery.
6. Tenant-scoped activity and basic usage summaries.
7. Student, channel and broader configuration areas as their implementation phases are reached.

Do not render unimplemented sections as if they work. Build a complete, reliable slice before broadening the dashboard.

## 9. Architecture and data ownership constraints

- One BRVIN Teachers application, shared runtime Worker and separate application D1.
- One tenant record per teacher; no per-teacher Worker, database or repository by default.
- BRVIN remains the sole authority for projects, collections, source records, ingestion, storage, indexing, readiness, grants and retrieval.
- Tenant UUID/reference is owned by BRVIN Teachers.
- BRVIN project/collection/source IDs and references are owned by BRVIN.
- The consumer uses actual BRVIN project IDs in server-side mappings and in the frozen v2 retrieval calls.
- The Operator Console must not write directly to BRVIN D1 or call GCS/AI Search.
- Existing Parmar AI, Fatman and AskMoina production experiences are outside this console and must not be modified as a side effect.

## 10. Acceptance criteria for the console

- An operator can create a teacher with an arbitrary custom name; the system returns a unique immutable tenant UUID and tenant reference.
- Identical teacher names are allowed and remain distinguishable by IDs.
- An operator can rename the teacher without changing identifiers.
- Project, collection and source creation each allocate identifiers at the correct parent scope, atomically and without reuse.
- UUID/reference details are copyable; users cannot supply or override system IDs.
- One teacher's workspace lists only its own projects and explicitly shared records.
- Shared collections retain their original identity and origin label.
- Source readiness reflects BRVIN state and cannot be manually forced.
- Interrupted cross-system operations can be safely retried without duplicate records.
- Role-based authorization is enforced server-side and cross-tenant negative tests pass.
- The dark interface is legible, keyboard-accessible, responsive and respects reduced motion.
- No synthetic teacher/source records are inserted into production to make the dashboard look populated.

## 12. Persistent source-processing stepper

The source progress experience is a modal stepper inspired by the supplied vertical checklist reference, adapted to the Operator Console's approved charcoal design system.

### Five authoritative stages

1. **Secure PDF upload** — browser-side resumable 8 MiB chunks into BRVIN's private storage.
2. **Vision OCR** — the server-side Google Cloud Vision operation.
3. **Page indexing** — BRVIN indexes each extracted page while preserving source and physical page provenance.
4. **Retrieval quality checks** — the Core workflow verifies that scoped retrieval returns page-grounded evidence.
5. **Ready** — BRVIN confirms the source is eligible for retrieval; the UI never sets this state itself.

The active stage uses a restrained rotating four-dot loader. Completed stages show a green check and completed connector; pending stages remain neutral. A failed stage alone turns red, displays a failure marker and renders the exact Core event/error message in a readable error panel. Status is conveyed through text and icons as well as color. Respect `prefers-reduced-motion` by disabling the rotating loader.

### Reopening and lifecycle

- Opening **View progress** on a source calls the authenticated, tenant/project/collection-scoped `GET .../sources/:id/status` management route.
- The modal renders Core's persisted import state, Vision/Workflow status and source activity events. It does not reconstruct status from browser memory or mutate BRVIN records.
- Poll every four seconds while the modal is open and visible; back off while the document is hidden. Stop polling when the modal closes or Core confirms Ready. Reopening fetches the latest server state immediately.
- Closing the modal never cancels Core's Workflow. After the secure upload is complete, OCR, indexing, recovery and retrieval QA continue on BRVIN Core even if the operator closes the page.
- The chunk transfer itself is initiated by the browser. If the browser closes before the PDF is fully transferred, the server retains the resumable upload offset; the operator selects the same PDF again so its SHA-256 identity resolves the existing source and upload session rather than creating a duplicate.
- If the status endpoint temporarily cannot be reached, show a neutral connection/retry notice. Do not mark a pipeline stage failed because of a transient UI polling error.
- An actual upload-chunk error marks Secure PDF upload red. A Core event tagged `vision`/`ocr`, `index_chunk`/`repair_chunk`, or `quality_check`/`verification` marks the corresponding OCR, indexing or retrieval-QA stage red. Retention/cleanup warnings after READY are not ingestion-stage failures.
- The modal's final state must read **Ready** only when BRVIN Core reports the completed/ready source state. Never optimistically display completion from the browser's successful upload alone.


### PDF page map and automatic page count

The source-upload form does not ask the operator to enter a PDF page count. BRVIN Core derives the count from its completed Google Vision per-page output inventory, validates the consecutive page files, and sends the authoritative value through the existing source-status response. Until that count is verified, the modal states that the page count is being detected and does not display a fabricated total.

A page map sits below the five-stage progress stepper inside the same scrollable source-progress dialog. It renders one compact tile per detected PDF page and uses Core's saved per-page indexing snapshot to distinguish indexed, running, queued, failed and waiting pages. The dialog remains the only progress surface; the map is lower in the content so operators can scroll to it without a second popup. The UI must not make additional AI Search status requests to build the map.
