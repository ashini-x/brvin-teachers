# Human-Readable Reference Identifier Policy

**Status:** TCH allocator and Core PRJ/COL/SRC metadata/allocators deployed; no real production teacher or knowledge reference has yet been issued  
**Decision date:** 6 November 2026  
**Applies to:** New BRVIN Teachers tenant and teacher-knowledge records only  
**Repositories:** `ashini-x/brvin-teachers` and `ashini-x/parmar-ai`

This policy defines operator-facing reference codes for teachers (tenants), subject knowledge projects, collections and PDF/document sources. It does not replace database identifiers, BRVIN IDs, or authorization.

## 1. Decision

Use hierarchical, human-readable reference codes. Each child sequence restarts at `001` inside its own parent. The complete code includes the parent path, so repeated local numbers are expected and unambiguous.

**Never use one platform-wide counter for every project, collection or source. Never derive the next number by counting current rows.**

## 2. Reference formats

| Record | Format | Example |
|---|---|---|
| Teacher / tenant | `TCH-{tenantNumber}` | `TCH-000001` |
| Project / classroom | `{tenantRef}-PRJ-{projectNumber}` | `TCH-000001-PRJ-001` |
| Collection / bookshelf | `{projectRef}-COL-{collectionNumber}` | `TCH-000001-PRJ-001-COL-001` |
| Source / PDF | `{collectionRef}-SRC-{sourceNumber}` | `TCH-000001-PRJ-001-COL-001-SRC-001` |

Tenant numbers use at least six digits. Project, collection and source numbers use at least three digits. These are minimum display widths, not maximums: after 999, the next value is `1000`; values are never truncated or wrapped.

The prefixes are fixed:
- `TCH` — teacher/tenant
- `PRJ` — BRVIN knowledge project
- `COL` — BRVIN collection
- `SRC` — BRVIN source/document

Application and environment identities continue to use their existing BRVIN-generated IDs. This decision does not introduce an `APP` or `ENV` reference-code scheme.

## 3. Counter scope and restart rules

Counters are scoped to their immediate parent:

1. Tenant numbers are allocated globally within BRVIN Teachers.
2. A teacher's project counter starts at `001` and increments only among that teacher's projects.
3. Each project's collection counter starts at `001`.
4. Each collection's source counter starts at `001`.

Example: Teacher `TCH-000001` has two projects. Both projects may have `COL-001` and `COL-002`. Every collection may have `SRC-001`, `SRC-002` and `SRC-003`. Their complete references remain distinct because the parent segments differ.

For two teachers, the first project of each is also `PRJ-001`; the tenant segment makes the complete code unique.

## 4. Worked example

Teacher `TCH-000001` has two projects, each with two collections, each collection containing three sources:

- `TCH-000001-PRJ-001`
  - `TCH-000001-PRJ-001-COL-001`
    - `...-SRC-001`
    - `...-SRC-002`
    - `...-SRC-003`
  - `TCH-000001-PRJ-001-COL-002`
    - `...-SRC-001`
    - `...-SRC-002`
    - `...-SRC-003`
- `TCH-000001-PRJ-002`
  - `TCH-000001-PRJ-002-COL-001`
    - `...-SRC-001`
    - `...-SRC-002`
    - `...-SRC-003`
  - `TCH-000001-PRJ-002-COL-002`
    - `...-SRC-001`
    - `...-SRC-002`
    - `...-SRC-003`

The local suffix repeats intentionally. The complete hierarchical reference identifies the record.

## 5. Two identity layers — mandatory

Every record has two distinct identity concepts:

### Permanent system identity

- The BRVIN Teachers tenant has an internal immutable database ID (normally a UUID) generated by the application database.
- BRVIN projects, collections and sources retain their BRVIN-generated internal IDs.
- Database relationships, RPC calls, retrieval, grants and authorization use these real system IDs.

### Human-readable reference

- The reference code is an operator-facing label for support, administration, audit displays and troubleshooting.
- It is not a password, token, capability, permission or proof of ownership.
- Knowing or guessing a reference code must never grant access.
- Never substitute a reference code for the opaque BRVIN `projectId` accepted by the v2 RPC.

The full reference is a stable origin/registration reference, not an access-control mechanism and not a substitute for displaying the record's current relationships.

## 6. Record ownership across the two repositories

The owner that creates the record allocates and persists its reference:

- `brvin-teachers` owns teacher/tenant records and allocates `TCH` references in its own application D1.
- BRVIN in `parmar-ai` owns knowledge projects, collections, sources and their actual internal IDs. BRVIN must allocate and persist the corresponding `PRJ`, `COL` and `SRC` references in its own registry.
- During teacher onboarding, the tenant's non-secret `TCH` reference is supplied to BRVIN as the external teacher/owner reference for the knowledge project. It is a correlation label only, never trusted as authorization.
- `brvin-teachers` stores the tenant-to-BRVIN-project mapping using the actual opaque BRVIN project ID. It may retain the human-readable reference for display, but must not create a competing source/collection registry or copy source content.

Because the BRVIN records are owned by the core repository, implementing the complete hierarchy requires coordinated changes to BRVIN Admin/registry and the consumer's tenant/project mapping. Do not implement only one side.

## 7. Sharing, reorganisation and lifecycle

- A collection or source shared with another project keeps its original reference. A grant changes who may retrieve it; it does not create a new identity or renumber the record. The receiving project should show that the material is shared from its originating teacher/project.
- A source's reference identifies its original registered collection. Additional collection membership or direct-book grants do not silently rewrite that reference.
- A rename changes the display name, not the reference.
- A move/re-parent operation must not silently rewrite a reference. Preserve the permanent system ID and original reference. If a genuinely new tenant-owned copy/record is required, create a new BRVIN record under the destination hierarchy with a new reference; retain the old record/reference for history and apply the normal grant/revocation policy.
- Deleted, archived or retired numbers are never reused. Preserve tombstones or equivalent allocation history.
- Existing Fatman, AskMoina and other pre-existing BRVIN records are not retroactively renumbered by this policy. Any migration/backfill requires a separate reviewed decision and compatibility plan.

## 8. Allocation and integrity requirements

When implementation is authorized:

- Allocate each number atomically in the database owned by the record creator, using a per-parent counter/sequence and transaction or equivalent concurrency-safe operation.
- Enforce a unique constraint on each complete reference code.
- Concurrent teacher/project/collection/source creation must never produce duplicate references.
- Gaps are acceptable; duplicate or reused numbers are not.
- Do not calculate the next value with `COUNT(*) + 1`, scan current rows for the maximum without a lock, or reuse a number after deletion.
- Validate parent ownership before allocating a child reference.
- Audit creation, archive, sharing and any future reorganisation using permanent system IDs and reference codes, without logging student private data or secrets.
- References should be shown in the protected Operator Console and BRVIN Admin where useful; do not expose internal IDs or administrative metadata unnecessarily to students.

## 9. Scope and implementation status

Tenant reference generation (`TCH-...`) is implemented in the deployed BRVIN Teachers application D1. Core PR #107's project, collection and source reference columns, per-parent counters and management operations are deployed. Consumer PR #2's screens that display these references are also deployed. The production BRVIN registry still has no `brvin-teachers` application/environment record; the management service therefore fails closed until that identity is registered and its UUID is deployed into the consumer config. The app D1 contains zero teachers and zero project mappings; no production tenant/project/collection/source has been created and no reference code has been issued.

Before implementation, the two repositories must agree on:
- the exact BRVIN D1 schema/migration for project, collection and source references and per-parent counters;
- how BRVIN Admin receives and verifies the external tenant reference;
- the immutable origin/ownership relationship for collections and sources, including direct-book grants and shared collections;
- how references appear in the Operator Console and BRVIN Admin;
- safe allocation, concurrency, deletion, archival, sharing and isolation tests;
- migration/rollback and compatibility behavior.

The coordinated Core and consumer releases are deployed, but the production application environment is not registered and no real records have been created. Use the new reference hierarchy only through the deployed owner-side creation operations after activating the registered environment. Never hand-invent reference codes, seed synthetic production records or change the frozen v2 retrieval contract to carry these display codes.
