This document describes the separate private management capability used for classroom, collection and PDF source administration. It is not the BRVIN retrieval v2 contract.

## 1. Boundary

BRVIN Teachers owns teacher identity and its application D1 database. BRVIN Core in parmar-ai owns projects, collections, source records, GCS objects, OCR, indexing, readiness, source/project grants, retrieval quota and Core activity.

BRVIN Teachers must never access BRVIN D1, GCS or AI Search directly. It calls the named `BrvinTeachersManagementApi` WorkerEntrypoint on the existing `parmar-ai` Worker through a same-account Cloudflare Service Binding. This is a private Worker-to-Worker call, not an Internet-facing management REST route.

The existing `brvin-service` Worker and frozen `BrvinRetrievalApi` remain retrieval-only and unchanged.

## 2. Trusted application identity

It calls the Access-protected, no-store `GET /operator/api/brvin-management/health` endpoint. The endpoint invokes `BRVIN_MANAGEMENT.health()` and reports `Management connected` only when Core confirms the registered active application environment. Missing, rejected or unreachable management RPCs report `Management unavailable`. The independent BRVIN Admin proof check still verifies `BRVIN_SERVICE` / `proveConnectionV2`; do not conflate the two connections.

- Named export: `BrvinTeachersManagementApi`

The environment ID is generated by BRVIN Admin and placed in the consumer's deployment-controlled `cloudflare.config.ts`. It is not accepted from the browser, URL, request body or arbitrary headers. An unknown, malformed, suspended, revoked or misconfigured environment cannot use the management entrypoint.

## 3. Identity and ownership mapping

The consumer loads a teacher by its immutable internal tenant UUID from app D1. It obtains the TCH reference from that trusted row and supplies the reference to Core. Browser-supplied tenant references are never treated as authorization.

Core stores the owning application ID and external tenant reference on each managed project/collection/source record. It also retains its own opaque internal IDs. The app stores the resulting opaque BRVIN project ID and its project reference in `tenant_brvin_projects`; collection and source references are returned by Core as needed.

Human-readable references are display/support labels, not credentials or permission tokens:

- `TCH-000001`
- `TCH-000001-PRJ-001`
- `TCH-000001-PRJ-001-COL-001`
- `TCH-000001-PRJ-001-COL-001-SRC-001`

Counters are allocated in BRVIN's own D1 and are parent-scoped, atomic, and minimum three digits. Existing BRVIN/Fatman/AskMoina records are not backfilled or renumbered.

## 4. Management methods

The deployed private WorkerEntrypoint exposes these operations:

| Method | Purpose |
|---|---|
| `health()` | Confirm that the trusted application environment is registered and active |
| `listTeacherProjects({tenantReference})` | List the active projects owned by the teacher and granted to BRVIN Teachers |
| `createTeacherProject(...)` | Create a subject classroom, allocate PRJ reference and create app-project grant |
| `updateTeacherProject(...)` | Rename a classroom or change its subject/description without changing its ID/reference |
| `updateTeacherProject(...)` | Rename a classroom/change its subject or description without changing its ID/reference |
| `listTeacherCollections(...)` | List collections explicitly granted to a teacher's project |
| `createTeacherCollection(...)` | Create a collection/bookshelf and grant it to its originating project |
| `updateTeacherCollection(...)` | Rename an owned bookshelf without changing its origin or reference |
| `updateTeacherCollection(...)` | Rename an owned bookshelf without changing its origin or reference |
| `grantTeacherCollection(...)` | Share an owned collection with another project belonging to the same teacher |
| `revokeTeacherCollection(...)` | Revoke that project's collection and direct source grants |
| `listTeacherSources(...)` | List source records in an authorized collection |
| `startTeacherSourceUpload(...)` | Register a PDF import and allocate/return SRC reference |
| `uploadTeacherSourceChunk(...)` | Transfer a bounded resumable upload chunk |
| `completeTeacherSourceUpload(...)` | Start the existing OCR/index Workflow |
| `resumeTeacherSourceUpload(...)` | Resume an eligible failed import using its saved state |
| `getTeacherSourceStatus(...)` | Read live import/index/QA status |

The methods validate tenant ownership, project grants, collection grants and source origin at Core. The consumer performs its own teacher-record lookup before calling the binding. Classroom and collection renames modify display data only; internal IDs and references do not change. Only the originating classroom may rename a collection or add new PDF sources to it. A receiving classroom can view a shared collection and its ready sources, and can revoke its own grant without changing the source's origin.

Project/collection creates use a stable request ID and a SHA-256 hash of the submitted details. Repeating the same request is idempotent; reusing the request ID with different details returns a conflict. The UI holds a request ID constant while a create is being retried.

## 5. PDF upload lifecycle

The Operator Console:
1. accepts a teacher-approved PDF and display title;
2. calculates SHA-256 in the browser;
3. requires explicit acknowledgement that Google Cloud OCR can incur charges;
4. starts the Core import without a client-supplied page count; Core derives the exact count from its completed Vision page-output inventory before indexing;
6. transfers the file in chunks no larger than 8 MiB;
7. asks Core to start or resume the existing ingestion Workflow;
8. lists the real source lifecycle and indexed page count.

Core reuses the existing private GCS resumable upload, Google Vision OCR and Cloudflare Workflow pipeline. The consumer never receives a GCS upload-session URI, provider credential or OCR object. Source references are allocated by Core after the source record exists.

The new import deduplication scope is the originating BRVIN collection. Identical bytes uploaded into two different collections create independent source records. A retry within the same collection can reuse its import. Existing Fatman/legacy imports retain their legacy deduplication scope.

The UI cannot manually mark a source READY. Only the existing BRVIN ingestion/QA process can make a source retrieval-ready. A completed upload means transfer/processing was started; it does not mean the source is indexed or retrievable.

## 6. Sharing and revocation

A collection is created with a grant to its originating classroom. An operator may share an owned collection with another project belonging to the same teacher. Cross-tenant collection sharing is not enabled by this initial management API.

Revoking a collection from a target project removes:
- that project's row in `brvin_project_collections`;
- direct `brvin_project_books` grants for sources originating in that collection.

The originating project's collection grant cannot be revoked through this API. Retrieval still rechecks Core project/source grant and readiness on every request.

## 7. Application API routes

All routes below are under the Cloudflare Access-protected `/operator` surface and resolve the teacher from app D1 before calling Core:

- `GET/POST /operator/api/teachers/:tenantId/projects`
- `PATCH /operator/api/teachers/:tenantId/projects/:projectId`
- `PATCH /operator/api/teachers/:tenantId/projects/:projectId`
- `GET/POST /operator/api/teachers/:tenantId/projects/:projectId/collections`
- `PATCH /operator/api/teachers/:tenantId/projects/:projectId/collections/:collectionId`
- `POST/DELETE /operator/api/teachers/:tenantId/projects/:targetProjectId/collections/:collectionId/share`
- `PATCH /operator/api/teachers/:tenantId/projects/:projectId/collections/:collectionId`
- `POST/DELETE /operator/api/teachers/:tenantId/projects/:targetProjectId/collections/:collectionId/share`
- `GET/POST /operator/api/teachers/:tenantId/projects/:projectId/collections/:collectionId/sources` (new source uploads are accepted only from the originating classroom) (PDF upload start is allowed only from the originating classroom)
- `POST .../sources/:importId/chunk`
- `POST .../sources/:importId/complete`
- `POST .../sources/:importId/resume`
- `GET .../sources/:importId/status`

Mutation routes require same-origin requests. Raw PDF chunks have a same-origin check, an 8 MiB limit and explicit byte offset/total-size metadata. The Core side independently validates project, collection and source ownership.

## Automatic PDF page-count detection and source page map

New collection-scoped BRVIN Teachers uploads do not submit a page count. The browser sends only the source title, filename, SHA-256 fingerprint, file size and explicit OCR-cost acknowledgement. Core stores page count as an internal not-yet-detected sentinel, then derives the exact count after Vision completes by validating the isolated per-page output inventory (output-1-to-1.json through output-N-to-N.json). Core requires a complete consecutive sequence, rejects gaps, duplicates, truncated inventories and counts above 2,000, and persists the verified count in its own source/import records before indexing begins. The legacy Fatman importer and its 538-page default are unchanged.

The source-progress dialog includes a scrollable page map below the five-stage stepper. It displays every physical PDF page with the latest Core monitor status: indexed, running, queued, failed or waiting. Core includes the compact page-state snapshot in the existing source-status activity response. The consumer does not query AI Search or Core storage directly and does not create a second ingestion engine; the retrieval v2 contract remains unchanged.
